# v0.5 plan: projects, funding, eligibility, selection, certification

Implementation plan for "Eligibility, selection and certification (designed for v0.5)" in docs/DESIGN.md. Requirements are in docs/FUNCTIONAL-SPEC.md (sections J, E, C, M, FR, plus I-7 and D-1 to D-3). One CLT's draft lottery procedure shaped the selection design.

v0.5 also includes SharePoint document storage (Property and Household libraries), already merged (PR #3). This plan adds a third library, Project Documents.

Nothing here is built yet. Names below are logical names without the `clt_` prefix, following schema.py.

## Revision 2026-11-09: two apps

Decided after this plan was written; it overrides the sections below where they differ. See docs/DESIGN.md, "Two apps, one environment" and "Blind selection and identity".

- Split the build into two solutions: the core (`CLTStewardship`) and `CLTIntake`. Project, Project home, Project priority, Project funding, Selection round, Selection entry, Application, Income source, Debt, Asset, Certification, Eligibility check, Document requirement, Document checklist item and Notice log go in `CLTIntake`. Funding program, Property funding, Income limit set and Income limit stay in the core.
- Names are visible on intake records (revised 2026-11-09: no Applicant identity table). The lottery is blind by process: frozen screener answers, a locked-selections team, a check number at the lock, dice, formula ranking, no manual rank edits.
- Household keeps its certification fields (filled at handoff). Drop "Replace the certification fields with a Current certification lookup".
- Documents: copy at the handoff, not at Certify (D-flow-1 moves to the handoff flow).
- Security: Intake reviewer, Certifier and Lottery Administrator roles, the Locked selections team, and auditing on Selection round and Selection entry, are part of the intake build.
- Selection entry: add submitted on, chances, ranking key, status reason (no adjusted rank). Selection method choice: Lottery, First come first served; plus Rolling (yes or no, default yes) for first come first served. Resale project: List source (Own selection, Reuse a recent list) and a lookup to the reused round.
- Required documents: Document requirement (per funding program: name, instructions, per household or per member, dated within N days, required) and Document checklist item (certification, member, requirement, status, received on, reviewed by, note). Certify warns on open items and records them.
- Notice log and message templates for screened-out, not selected, invited and reminder notices.
- Weighted lottery: new tables Project lottery factor and Entry factor; the draw flow computes key = u^(1/chances).
- Test data: sandbox Cognito forms (screener form 6, full application form 5) hold 12 made-up households, entries 6-1 to 6-12, covering over-income, too-low income, recent bankruptcy, current owner, no local tie and an accommodation request.
- New flow: handoff at "Purchase and sale agreement signed" (H-1).
- Build-tool work: done 2026-11-09. Tables carry `solution="intake"`; `build_app.py --app intake` builds the second app from `app_spec_intake.py`. Dev keeps one solution until deployment.
- Built 2026-11-09 (milestone 1): choices; Income limit set, Income limit, Funding program, Property funding (core); Project, Project priority, Project funding, Project home, Lottery factor, Selection round, Selection entry, Entry factor, Certification, Eligibility check, Document requirement, Checklist item, Notice (intake); selection columns on Application; certification lookup and "adjusted or excluded because" on income, debt and asset lines; the WA HTF starter row; both apps' navigation, views and forms.
- Simplified: applicants are ordinary Household and Household member records (names visible), so the handoff updates the household and creates the occupancy instead of copying people. Application stage reuses the existing choice with new values added (no retirement needed).
- Deferred to the next milestone: purchase financing (Loan, sale ratios, salestatus2), household demographics, current housing costs on Application, formula columns, command bar buttons, flows (pre-screen, Unique IDs, lock and check numbers, draw, invites, certify, handoff), the verifier workbook, and the HTF report.
- Screener is generic (2026-11-09): no project choice on the screener. Applications come in without a project and staff add them to one by bulk edit. Built: the screener intake flow (HTTP post from Cognito, `flows_intake.py`), the "Not in a project yet" view, and the intake app's Start here page.
- Known item for the solution split: the shared Household form lists applications and certifications, so the core app includes those two intake tables (`APP_EXTRA_TABLES`).

### 1.6 Seed data

- **Funding programs:** a new `SEED_ROWS` mechanism (1.8). It creates rows only when the table is empty, the same rule as `SEED_LISTS`. The first row is **WA HTF Homeownership**, with the rules in DESIGN.md: gross annual income; housing ratio 38%, including all seven items; total debt 45%, including all three; first-time buyer required; no asset limit; validity and education blank until verified; demographics: Ethnic origin (HTF), Special needs; report format HTF Homebuyer Information Form.
- **Income limits:** no seed and no loader. Staff enter them yearly in the app. (Later option: a "Get limits from HUD" flow using HUD USER's Income Limits API.)
- **Project priorities:** no seed; each project sets its own, with a "Copy priorities from another project" button.

### 1.7 Retired items

Add to `RETIRED`. Removing them needs `--remove-retired`, which deletes their test data in Dev (the owner's go-ahead first).

- **Columns:** application.stage, application.ami100, household.certificationdate, household.certificationexpires, household.certifiedhouseholdsize, household.certifiedincome, household.certifiedamipercent, sale.status
- **Choices:** applicationstage, salestatus
- **Hand-made columns** on Application (verifiedannualincome, verifiedassets, verifiedmonthlydebt, incomepctami): Step 4 hasn't been done, so they probably don't exist. If they do, delete them by hand before the schema run. Update docs/STEP4-columns.md to move them to Certification.

Why replace stage and sale status instead of editing them: the builder only adds choice options. It never renames or removes them, on purpose, so existing numbers stay stable. A new choice plus `--remove-retired` follows the v0.3 pattern. The new column names (pipelinestage, status2) can keep the display names "Stage" and "Status".

Not retired, but now unused: the "Document type" value in the List name choice. Leave it.

### 1.8 Builder changes (`build_schema.py`)

1. **`datetime` column kind:** DateTimeAttributeMetadata with Format DateAndTime, behavior UserLocal.
2. **Lookups to system tables:** allow a LOOKUPS parent like `systemuser` without the `clt_` prefix (ReferencedAttribute `systemuserid`).
3. **Whole-number and decimal defaults:** Dataverse has no metadata default for them. Set the project defaults (buffer 110, invites 10 and 2, deadline 15, waitlist 12) with a form business rule.
4. **`SEED_ROWS`:** seed rows for any table when it's empty. Choice and multi-select values are given by label and mapped through choice-values.json.
5. **Table and lookup retirement:** already built in the v0.5 portfolio cleanup (`RETIRED["tables"]` and `RETIRED["lookups"]`), along with display-name sync.
6. **Spec checks:** names with the prefix still at most 40 characters; lookups to system tables allowed in `check_spec`.

## 3. Formula and rollup columns (by hand)

Added to docs/STEP4-columns.md. Schema names must match the ones `build_app.py` places with `?`.

**Rule: rollups only show totals on screen.** No flow reads a rollup, because rollups refresh about hourly. Flows add up the rows themselves.

|---|---|---|---|

| certification | verifiedmonthlydebt | Rollup | Debts (Certification), same filter, sum of verified monthly payment |

## 6. Lottery verifier and HTF report

**Lottery verifier** (`docs/reference/lottery-verifier.xlsx` and `tools/verify_lottery.py`)
- The workbook: paste the round's entries exported by Unique ID (Unique ID, bedrooms, tier) and type the seed. Column formulas: `s1 = MOD(seed * 16807, 2147483647)`, then `MOD(previous * 16807, 2147483647)` filled down in Unique ID order; lottery number = s / 2147483647; then ranks per list with SORTBY on tier and lottery number. The products stay below 2^53, so Excel's arithmetic is exact.
- The script does the same, for a second independent check and for the tests.
- Publish the verifier with the procedure so applicants and auditors can use it.

**HTF Homebuyer Information Form (FR-1)**
- One per homebuyer, from Household, Certification, Sale, Loans, Property and Project funding.
- **Recommended:** fill a copy of the Commerce workbook with a flow using the Excel connector (template stored in SharePoint). The workbook's own formulas then calculate the limits and ratios, so they match what Commerce expects.
- **Alternative:** a Word template (Dataverse document templates) or a Power BI paginated report. Easier to maintain, but it isn't the Commerce file.
- Map every workbook cell to a column first, using the state Housing Trust Fund homebuyer information workbook (not included in this repo). Construction type, housing type and building status aren't tracked in the app; staff fill them in on the form.

## 8. Hard or impossible in Dataverse or Power Automate, and alternatives

1. **A lottery that can be checked later.** Power Automate's `rand()` can't be seeded, so a draw made with it can't be repeated.
   - **Chosen:** the Board Observer rolls dice for a seed at the draw, after the pools are locked, and the flow uses the published Park-Miller formula (fits Power Automate's 64-bit integer maths). The verifier workbook reproduces it exactly.
   - **Watch for:** the seed must be chosen after the pools lock and in front of the Observer, or someone could try seeds in advance. The round refuses a seed entered before Pools locked.
   - **Fallback:** draw in Excel under the current procedure and import the ranked lists; the app checks the IDs match the locked pools and the ranks follow tier then number.
2. **Locking certified records and their lines.** Form business rules only lock the form; data can still be edited through views, Excel or the API.
   - **Recommended:** ownership. Staff roles get Write at User level for Certification, Income source, Debt and Asset. At Certify, the flow assigns the certification and its lines to a "Certified records" team that staff aren't in (cascade assign), so staff can read but not change them. Re-certify assigns them back. Add business rules too, so the form shows them as locked.
   - Alternative: a synchronous plug-in (C# or a Power Fx low-code plug-in). Stronger, but it's code (N-2) or a feature to verify first.
3. **Locked pools and certified rounds.** Same as item 2: staff roles get Read only on Selection entry, the service account writes entries, and the round is assigned to the locked team at Pools locked. Status changes after that (Invited, Offered...) go through flows and buttons.
4. **Loan monthly payment as a formula.** A rollup can't add up a formula column. So monthlypayment is a plain column written by the Loan payment flow.
5. **Rollups lag about an hour.** Handled by the rule in section 3: rollups are only for display, and flows add up rows themselves.
6. **Derived demographics.** Formula columns can't read multi-select choice columns (verify in the maker portal), and can't count related rows (members by age). htfethnicorigin and htfspecialneeds are written by a flow and snapshotted at Certify.
7. **Land lease fee from the current Fee row.** A formula column can't search child rows by date. M-flow-1 copies it to the Sale (and to Certification as a starting value).
8. **Income limit lookup by county and size.** Formula columns can't query a table. The flows find the row and write the figures they used onto the check (value, limit and a "how it was worked out" note).
9. **Certify must refuse if any check fails.** A flow can't block a save. Status only becomes Certified through C-flow-1, which re-runs the checks first; the button is a convenience.
10. **"Is the actor a certifier?"** Use a Certifiers team and check team membership in the flow.
11. **Blind screening.** Model-driven apps can hide fields per form and view, but a user with read access can still open the Household.
   - **Default:** blind forms and views, no names on any lottery screen, a logged reveal, and the test in section 7 that keeps identifying columns off blind views.
   - **Strict option:** a column security profile "Applicant identity" on identifying columns, with non-identifying primary names for Household and Household member (primary name columns can't be secured, so names move to secured columns). Screeners lack the profile until the reveal; the Executive Director grants it. It costs everyday usability for staff who also work with homeowners, so it's worth it only if the Board wants enforcement rather than procedure.
12. **Copying uploads from Cognito.** The connector gives file links; downloading may need the HTTP action (premium, like the rest of these flows). Verify during the flow licensing test.
13. **Whole-number and decimal defaults:** no metadata default; use form business rules.
14. **Changing existing choices** (stage, sale status): the builder won't rename or remove options; new choices plus retirement (1.7).
15. **Board Observer may not be an app user.** Record the name as text; the signed certification in Project Documents is the evidence.
