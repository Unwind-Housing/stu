# Stu: project brief for Claude

Stu is an open source stewardship system for community land trusts (CLTs). Read this first. If someone has asked you to **install Stu in their environment, read `INSTALL.md` next and follow it with them step by step.** If you are changing Stu, read `CONTRIBUTING.md`, then `docs/ROADMAP.md` for what's next and `docs/DESIGN.md` for the full design record.

- Feature requests are logged in the **Feature requests** table at the bottom of `docs/ROADMAP.md`: add a row when someone asks for something or a gap turns up, and update its status when it's picked up or done.
- `docs/FUNCTIONAL-SPEC.md` defines what the product must do. Check changes against it.
- `docs/PLAYBOOK.md` is the running guide for whoever looks after the system: yearly jobs (HUD AMI limits), adding a screener form, troubleshooting. When you work out a procedure that will come up again, add it there.
- `CLAUDE.local.md`, if it exists, holds this installation's own details (environment address, accounts, the person's preferences). It is not committed. Create it during the install.

## What this is

A lean, low-cost way for a CLT to track properties, households, the occupancies that link them, annual verifications, insurance, homeowner requests, resale prices, sales, documents and the per-home ERRR (external repair and replacement reserve), plus intake: screeners, projects, pre-screening, selection, full applications and certification. It is built on **Microsoft Power Platform: Dataverse plus one model-driven app (Stu)**, and installed by running the build scripts in this repo against a CLT's own environment.

- **Maintainer:** Unwind Housing & Advisory Services LLC. MIT licence. Each CLT owns its own environment and data.
- **Online forms** (screener, full application, annual verification) live in a forms platform, currently Cognito Forms. The design is deliberately **forms-platform agnostic** (Cognito, Jotform, FormAssembly).

## Portability rules

Stu is installed at more than one CLT, and each one should be able to pull new versions and send improvements back.

- **Nothing client-specific in core.** `schema.py`, the app specs, flows, pages and tools must work for any CLT. No organization names, tenant addresses, account names or local place names except as clearly made-up examples.
- **Each organization has one folder, `clients/<name>/`:** `client.json` (name, environment addresses, service account, SharePoint site, branding), `forms/` (its form mappings), `samples/` (sample entries from its forms) and its own notes. `clients/example/` is the template and the only folder there that is committed. An organization's own folder stays on its machine, ideally as its own private git repository.
- **Never commit client data.** Real properties, households and applicants go in `export/`, which git ignores. Tests and examples use made-up people at `example.com`.
- **A CLT that needs something different** changes it in core in a way every CLT can use (a setting, a list value, a field), and sends it back as a pull request. It doesn't keep a private edit of `schema.py`.
- **Don't assume where documents live.** One organization keeps applicants' documents in SharePoint, another in Google Drive. Pages reach documents through a link pattern the organization sets, never through a SharePoint-only call. (The record folders Stu makes for properties, households and occupancies are SharePoint today; that is a known limit, not a pattern to copy.)
- **Prefer scripted steps to hand steps.** Where a step must be done by hand, write it in `INSTALL.md` or the playbook with exact menu paths.

## How the build works

- `schema.py`: tables, columns, global choices, lookups, alternate keys, seed list values, retired items.
- `build_schema.py`: creates the schema through the Dataverse Web API, inside the solution. It's idempotent: it never changes or deletes existing items, except `--remove-retired`, which deletes items listed in `RETIRED`, tables marked `documents=` in `schema.py`, which get SharePoint document management switched on (never off), formula columns, whose formulas are updated to match `schema.py`, and table and column display names, which are updated to match `schema.py` (labels only). `RETIRED` can hold columns, lookups, tables and choices. It also sets the solution version from `VERSION`.
- `--sharepoint-site <url>` on the schema build sets up per-environment SharePoint storage: the default site record, a library per `documents=` table (URL = table logical name, title from `schema.py`) and its document location. These are data, so each client environment runs it with its own site. `--sharepoint-folder DEV` adds a parent folder inside every library for an environment that shares the site with another one (for example a Dev environment that shares the production site): the folder flows then put new record folders in `clt_property/DEV/...`. The folder per environment is noted in `clients/<client>/client.json` (`sharepointFolder`).
- `app_spec.py`: navigation, views and work queues, main form layouts for the **Stewardship** side. `app_spec_intake.py`: the same for the **Intake & Selection** side.
- `app_spec_stu.py`: the one app staff use, **Stu** (`clt_Stu`). It defines nothing itself: it puts the two specs above into one app as two areas (the switcher at the bottom left of the sidebar). `build_app.py` builds Stu by default; `--app core` and `--app intake` still build one side as an app of its own, for a client that wants only that side. One app because per app passes are counted per person per app; who sees which side is down to security roles (step 8).
- **Guided processes:** anything with steps that must happen in order (lottery, sale, resale) gets a guided page inside Stu with an app feel, like Projects > Pre-screen: the page walks through the steps and the rules sit in a plain JavaScript function with Node tests. Not a separate Power App (that would cost another pass per person).
- Tables in `schema.py` carry `solution="intake"` when they belong to the intake side; untagged tables are core. Dev builds everything into the CLTStewardship solution for now; the split into two installable solutions happens at deployment.
- `build_app.py`: builds the app, its navigation, views and forms. It **overwrites** the forms and views it manages, so layout changes go in `app_spec.py`. Fields prefixed `?` are placed only if they exist (formula and rollup columns made by hand). File fields are dragged onto a form once by hand, and the script keeps them in place after that.
- `build_flows.py`: Power Automate cloud flows, defined in Python and deployed into the solution (`workflows`, category 5) with connection references. `--only "document folder"` deploys just the flows whose name contains that text and leaves the rest untouched (a full run overwrites a flow that was saved in the designer). Connections can't be scripted: the first time, someone picks them in each flow and turns it on. Flows are owned by whoever signs in, so the build signs in as `flowServiceAccount` from `clients/<client>/client.json` (or `--as`) and stops if anyone else signs in. Current flows: Property, Household and Occupancy document folders (`412 Fir St - P-00004` instead of Dataverse's `<name>_<GUID>`; the occupancy folder holds the ground lease, closing papers and ERRR requests, the household folder only application and certification documents), and the intake flows.
- **Intake flows and form mappings.** `flows_intake.py` (screener: the forms platform posts each entry to the flow's HTTP trigger; it upserts household, members and application, with no project) and `flows_full_app.py` (full application: finds the application by the form's Application Number, then email, and upserts the answers, members, income sources, debts and assets, never staff review fields). **Neither file names a question on any form.** Which question feeds which field is in the organization's mapping files, `clients/<name>/forms/*.json` (`form_mapping.py` explains the format; `python3 form_mapping.py <mapping> <sample entry>` checks one against a real entry). `screener.json` and `full-application.json` are the main forms and keep the flow names and IDs `CLT: Screener intake` and `CLT: Full application intake`; a form with different questions gets its own file (`screener-rental.json`) and the build makes it its own flow. Forms that are copies of each other share one mapping. A question a form doesn't ask is left out of the mapping and that field is left blank. `build_flows.py` picks the organization by `--url` (the folder whose `client.json` lists it) or `--client`. The full application trigger is named `manual`, the name the designer gives it, so a designer Save doesn't change the form's address. Annual verification intake (`flows_verification.py`, mapping type `annual-verification`): matches the entry on the form's hidden occupancy ID (the occupancy's record number, filled by the link), saves the answers on the open request and marks it Received, and starts or updates the occupancy's Insurance verification (To review when proof was attached and no help asked for, Needs contact otherwise) with a link to where the forms platform saved the uploads (`uploadsFolder` in the mapping). It never sets the occupancy's dates: staff closing and approving does. The intake triggers set `triggerAuthenticationType: All` (Who can trigger the flow: Anyone); without it a designer Save drops the signature from the address and the form's posts are refused.
- `tests/`: offline tests against a fake Dataverse. Run them before every commit.
- `webresources/`: small form scripts (`names.js`, `tips.js`) and the Start here pages (`overview.html`, `guides.html` for the core app, `intake.html` (Hub), `intake-guide.html` (How it works) `newproject.html` (New project: six guided steps that create a project with its homes and priorities in one request), `assign.html` (Add to a project: filter screeners, add ticked or all), `selection.html` (Buyer Selection: shows where a project is, step by step, and runs close applications, build the lists, lock, draw and certify) and `prescreen.html` (Pre-screen: tests a project's screeners against its rules and saves the result and one Eligibility check per test) for the intake app, sharing `pages.css` and `pages.js`), uploaded by `build_app.py` (`WEB_RESOURCES`, `PAGES`, `FORM_SCRIPTS` and `SCRIPT_LIBRARIES` in `app_spec.py`). The guides describe the real screens: when a form or workflow changes, update `guides.html` too. A little JavaScript for obvious conveniences is fine; keep it small.
- The pre-screen rules are one plain function in `webresources/prescreen.js`, with no Dataverse calls, so `tests/test_prescreen.py` runs them in Node on worked examples (the test is skipped with a message if Node isn't installed). Change a rule there and add an example to the test. The page (`prescreen.html`) only loads data, calls the function and saves. The monthly housing cost per home size comes from the project's **income bands** (`projectband`: a band of buyers by income with its interest rate, sale prices, mortgage payments and monthly costs per home size, made by the New project page). The pre-screen picks the band from the household's stated % of AMI; a household that fails at its band's cost but is within the income buffer of the cheaper band below, and would pass there, is Needs review. A project with no bands uses the monthly cost fields on the project.
- **Guided pages follow the New project pattern:** the rules (what to check at each step, and the record to send) are one plain file with no Dataverse calls (`webresources/newproject.js`: `check(state, step)` and `plan(state, choices)`), tested in Node by `tests/test_newproject.py`. The page (`newproject.html`) collects answers, shows one step at a time, and sends what `plan()` returns with `CLTPage.create()`. Related records go inside the same request (a deep insert, using the relationship's name, for example `clt_project_projecthome_project`), so Dataverse creates all of them or none. Nothing is saved until the last step.
- **The selection rules** (`webresources/selection.js`, tested by `tests/test_selection.py`): Unique IDs in order of first submission; one list per home size; a check number per list at the lock; the draw (ten dice digits give a seed, the published Park-Miller generator gives each household one lottery number in Unique ID order, lists ranked by tier then number); first come, first served ranks by first submission at the lock. Lists show Unique IDs only. The page loads household names in one place (`loadNames`), and only once the results are certified and someone has been invited, for the dashboard's table of invited households (`dashboard()` in `selection.js`: figures across the top, and each invited household as in, waiting or late). Steps that change several records (close, lock, draw) go through `CLTPage.batch()`, one change set, so they happen completely or not at all. Before the draw and before certifying, the page recomputes the check numbers and refuses if they differ from the ones saved at the lock. The draw is deliberately not a flow: it has to be reproducible by hand from the roll.
- **PDFs** are made in the browser by `webresources/pdf.js`, a small writer with no library (text, tables, rules, signature lines on US Letter). The selection page uses it for the lists at the lock and the ranked results, which include how to repeat the draw by hand. `tests/test_selection.py` checks the files' structure.
- **Invitations** (`webresources/invite.html`, rules in `invite.js`, `tests/test_invite.py`): after the results are certified, the page shows the email (Settings > Message templates, `messagetemplate`, with a starter row in `SEED_ROWS`; words in curly brackets are filled in per household), each household's own link (the project's **Full application link** with `{number}` swapped for the application number), and who is next on each list. The page is three steps: choose who, check and edit the email (with the link), then one finished email at a time with Copy buttons and a mailto link. Stu does not send email. Sent marks that one household in one batch: application stage and invite link, every list entry it has, the household's status, and a Notice row with the message.
- **Certification** (`webresources/certify.html`, rules in `certify.js`, `tests/test_certify.py`; FUNCTIONAL-SPEC C-1 to C-8): staff review each income, debt and asset line of a full application (Accepted, Adjusted with an amount and a reason, Excluded with a reason), set the certified household size and tick what they have confirmed. `certify.js` adds up the verified figures, works out % of AMI the way the application's own formula does, and runs the **pre-screen's tests** (`prescreen.js`) on them with no buffers, plus homebuyer education. Certify needs every line reviewed, every general test passing and both ratios passing for at least one home size the household is on a list for. Saving is one batch: the lines, the certification (figures, confirmations, expiry, home sizes certified for), the checks (stage Certification, replacing earlier ones), the application's stage, the household's certified fields, and its list entries (Approved where it passed, Ineligible where it didn't). The certification record is created on the first save. Stu never writes to the household.
- **Documents on the review page:** Stu never holds a file. The form saves uploads into the organization's share; the full application's raw entry (kept on its Form submission) names every file. `certify.js` `documents()` reads those names with no knowledge of the form (any answer that is a list of files), ties each to its line by the form's line ID and the payer, creditor or institution, and takes the folder's last name from the entry. The household's folder is the organization's documents folder (setting `ApplicationDocumentsFolder`, set from `clients/<name>/client.json` by `tools/apply_branding.py`; a project's **Application documents folder** overrides it) plus the folder name pattern (`ApplicationFolderName`, default `{last name} - Entry {entry number}`). Lines are tagged Income 1, Debt 1, Account 1 from the form's line numbers, the convention for naming dropped files. `place()` puts household-wide uploads beside the step they support, from the question's wording. The page only builds a link; it makes no SharePoint call.
- **Verification hub** (`webresources/stewardship.html`, rules in `stewardship.js`, `tests/test_regular.py`): Start here > Verification hub lists every current occupancy with three recurring checks (occupancy verification, insurance verification, staff walk-by), each Overdue, Due soon (30 days) or Up to date. How often each falls due is an organization setting in months (`OccupancyVerificationMonths`, `InsuranceVerificationMonths`, `WalkByMonths`; blank means 12). Never recorded counts as overdue. The date used is the newest of the one typed on the occupancy (`lastoccupancyverified`, `lastinsuranceverified`, `lastwalkby`, `lastcontact`) and the ones on its records (annual verifications received, insurance policies verified, `walkby` and `relationshipnote` rows), and the page writes the newest back to the occupancy when it loads, so views on those dates are right. Record on a row adds a walk-by or relationship note, or sets a verified date, in one batch. The page leads into Occupancy verification: Start occupancy verifications (households overdue or due soon with no open request, `toAsk()`) and Ask this household open `verify.html` with `data=occupancies=<ids>`, which ticks just those; a row with an open request shows Asked.
- **Occupancy verification** (`webresources/verify.html`, rules in `verify.js`, `tests/test_verify.py`): Activities > Occupancy verification starts each household's yearly request as an **Online form** or a **Paper** copy (`annualverification.method`). Paper requests are opened at once (status Due) and wait to be closed by hand. Online ones go through the Invite pattern: the email (a message template of type Annual verification where that list is installed, else the built-in words), then one finished email at a time with Sent or Skip; Sent creates the request with its `verificationcode`. Each household's link comes from the organization setting `VerificationFormLink` and carries the year, the household's record number and the code: where the link has `{year}`, `{household id}`, `{code}` they go there (any platform); a plain Cognito link gets `?entry={...}`, any other plain link gets `?year=&householdId=&code=`. Close records the findings and sets the occupancy's Last occupancy verification. Not built yet: the flow that takes the form's reply and closes the request.
- **Follow-ups and improvement credits** are lists on the occupancy form (`followup`, `improvementcredit`). An improvement credit's Current value is a formula column (straight line by the day over its depreciation period); `resale.js` `creditValue` is the same sum for the Resale page, and the Verification hub and Resale pages keep the occupancy's Improvement credits total (which feeds Maximum resale price) in step with the list. `tips.js` `resaleTerms` hides the Appraisal share terms section unless the formula is appraisal based.
- **Insurance verification** (`webresources/insurance.html`, rules in `insurancecheck.js`, `tests/test_insurance.py`): Activities > Insurance verification. The page has the same three steps and requests list as Occupancy verification (choose who, the email, send; form link in the `InsuranceFormLink` setting). Each record (`insuranceverification`, tied to the occupancy) is Requested (the household has been asked), To review (proof to look at), Needs contact (the household asked for help or sent nothing), Issue found (saved, still open), Approved or Cancelled. Only an approval sets the occupancy's Last insurance verification date. The Verification hub shows an open one on the home's row (In progress or Needs contact) and opens it; `verify.html` and `insurance.html` take `data=open=<id>` to open one record.
- **Resale** (`webresources/resale.html`, rules in `resale.js`, loan sums in `loan.js`, `tests/test_resale.py`): Activities > Resale is a guided page over a Sale record of type Resale, so it can be left and resumed. Five steps: start (home and notice date, which creates the sale), price (formula price plus added value is the maximum resale price; loans owed to the organization, other credits and debits give what the seller is left with; saved onto the sale), buyer (a certified household, or a link to New project), contract (the price may be above the maximum: the seller's side stops at the maximum and the rest is saved as `subsidyrecapture`; the home goes to Sale pending) and closing. Closing is one batch built by `closing()`: the buyer's occupancy (the seller's formula and limits, starting from this price and date), the sale closed and pointed at it (`$1`, the record the first change made), the seller's occupancy ended, the property and both households updated.
- **Loans** (`loan` table, on an occupancy): starting balance, rate, dates and a regular monthly payment. `loan.js` holds the sums (`payment`, `owed`) and the Loan form's `CLT.Loans.fill`, which suggests the payment and never overwrites one that was typed. What is owed assumes payments were made on time; staff type the real payoff on the Resale page.
- **Dates on pages:** show a timestamp with `CLTPage.day()`, which gives the local day; slicing the UTC string shows tomorrow's date in the evening.
- Form fields prefixed `!` in `app_spec.py` are read-only on the form.
- Tables marked `audit=True` in `schema.py` get auditing switched on (and auditing for the environment); see Related > Audit history on a record.
- `clients/<client>/client.json`: per-client settings (name, branding, SharePoint site). `tools/apply_branding.py` writes them into the environment variables (defined in `schema.py` `ENVIRONMENT_VARIABLES`) and themes the app header. Values and theme stay out of the solution.
- `tools/load_counties.py`: loads all 3,143 US counties into the County list, linked to their State (data, per environment; safe to re-run).
- `tools/import_records.py`: loads properties, households, members, occupancies and monthly fees from CSV files in a folder (templates and rules in `docs/templates/`). Dry run first; all rows are checked before anything is written; safe to re-run. Client data goes in `export/`, which git ignores.
- `tools/start_from_scratch.py`: for a **test** environment only, one command: deletes every record and project (`tools/reset_records.py`; lists, AMI limits, eligibility rules, source forms and templates stay), moves the old record folders in SharePoint to the recycle bin (only inside the `--sharepoint-folder` parent), loads a made-up portfolio of 20 homes (`tools/make_test_data.py` `build`) and adds made-up history to it (`history`: sales, insurance, loans, requests, follow-ups, ERRR, past verifications). Counts only unless given `--confirm <first part of the address>`. The procedure is in the playbook: Start from scratch and load test homes. Never run it without Simon's go-ahead.
- `tools/recalc_ami.py`: points every screener's AMI limits used at its county's newest HUD AMI Limits record (Stated income (% of AMI) is a formula over that link). Run it after loading a new year's limits; the intake flow links new screeners.
- Formula columns are `fx(...)` columns in `schema.py` (Power Fx with internal names; every money column wrapped in `Decimal()`, and a blank money value reads as 0, so test it as `Decimal(x) = 0`, never `IsBlank`; numbers in `Text()` need a format, `Text(x, "0")`; choices as `[@'Choice display name'].'Label'`; at most 1,000 characters, so split a long one into two columns; `--check` catches the money and length rules). The schema build creates them after the lookups and updates a changed formula in place. Rollup columns, and the two formulas over them, are still created **by hand**: see `docs/STEP4-columns.md` (schema names must match).

## Conventions

- **Versions:** `main.sub`. Bump the sub version for each change set (v0.5, v0.6). v1.0 = first production go-live. For each release:
  - Update `VERSION`, `build_schema.VERSION` and the README version table.
  - Tag the commit `v0.x`, with a GitHub release titled `v0.x (YYYY-MM-DD)`.
  - The schema build stamps the solution version as `0.x.0.0`.
- **Branches:** work on a branch based on `main` and open a pull request. No stacked pull requests.
- **Never commit** credentials, `.env`, logs, `choice-values.json`, `.venv`, a flow's HTTP address (treat it like a password), anything in `clients/` except the example, or anything in `export/`.
- **Data safety:** no SSNs or bank account numbers in Dataverse. Applicants' uploaded documents stay in the forms platform until the household is certified; only certified households' documents are copied, into the restricted Household Documents library in SharePoint. Uploads from households never certified are purged on a schedule. Column security goes on income, asset values, dates of birth and demographics (step 8).

## Working with the person in front of you

They may be a CLT staff person, not a developer. Unless `CLAUDE.local.md` says otherwise:

- Use plain language and step-by-step instructions with exact menu paths. Give terminal commands one at a time, and say briefly what each one does.
- **Before running anything that changes an environment, say what it will do,** and which environment. Try a Dev or sandbox environment before production.
- **Before any command that opens a browser sign-in, say so first:** which organization, which account, and what it's for.
- Never run `--remove-retired` without their go-ahead, because it deletes data.
- Explain tradeoffs briefly, then recommend.
